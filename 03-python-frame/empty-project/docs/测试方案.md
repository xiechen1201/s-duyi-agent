# 测试方案.md

## 开发和测试的顺序

TLD（传统模式），先开发功能，再编写测试用例。

TDD，先编写测试用例，再开发功能。后续编写功能的时候目标就是让测试用例通过。

## 测试方案

- 单元测试

单个函数，类是否正确

问题：只想测试函数本身，不想测试 session 等环境。如何屏蔽呢？

1、Stub 模式

桩模式，少见

测试期间肯定不能真实的发送验证码。如何做呢？写一个假的发送验证码的函数。

通过 monkeypatch 实现。

2、Mock 模式

传递 mocker 参数。

mocker.patch() 替换函数或类。

好处：可以统计函数调用次数。

以上就是为了解决单元测试屏蔽外部环境的问题。

- 集成测试

覆盖率 = 运行的测试代码 / 所有代码

一般是在全量测试的时候查看覆盖率。

```
test:
	uv run pytest apps/web-service/test/unit/ apps/web-service/test/integration/ -q --cov=app --cov-report=term-missing --cov-fail-under=80
```

单测 + 集成测必须满足覆盖率要求。

- 系统测试

更贴近用户端真实运行的系统。

- e2e 测试

本身也属于系统测试。端到端测试，加强版系统测试。

测试一个业务功能链条：

例如：浏览商品 ==> 查看详情 ==> 购买商品 ==> 支付 ==> 订单确认

- 冒烟测试

系统的底线，必须要通过，否则会出现重大生产事故。
